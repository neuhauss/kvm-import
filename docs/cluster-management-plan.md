# SUSE HA cluster management plan

## Product goal

Add an extension-owned **Clusters** experience beside **Hosts**. It should guide an operator from existing SLES/KVM hosts to a reviewed, supportable SUSE Linux Enterprise High Availability cluster, and then provide a focused operational view. The extension must not patch Rancher or SUSE Virtualization. All UI, API integration, permissions, and audit records belong to this extension.

Use SUSE-provided and SUSE-supported components for the cluster workflow. The target stack is SLE HA with `crmsh`, Pacemaker, Corosync using `knet`, Hawk, QDevice/QNetd where appropriate, and supported fencing agents/SBD. Do not make cluster creation depend on community add-ons, third-party orchestration, or an alternative cluster manager.

## Design principles

- Discover and report first. A registered KVM host is not automatically a cluster-ready node.
- Separate read-only checks from changes. Show the commands/actions and their expected effects before each change.
- Keep each mutating phase explicit, resumable, and auditable. Do not send a single opaque shell script that installs and bootstraps everything.
- Use typed, allow-listed operations in the extension API. Reuse the current host connection and Rancher RBAC mapping; viewers can inspect, host administrators can prepare or operate.
- Do not store HA registration codes or `hacluster` passwords. Submit secrets only for the operation that needs them, and never write them to logs.
- Preserve the SUSE-supported `crm cluster init` and `crm cluster join` workflow. Avoid hand-building Corosync or Pacemaker configuration as a substitute for the SUSE tooling.
- Treat Hawk as a complementary native administration surface. Link or proxy it only after HA is detected, and only with an explicit secure authentication design.
- Make unsupported states clear. A green “connected” host status must never imply quorum, fencing, or HA readiness.
- Design the HA flow for operators with limited cluster experience: clear submenus, a visible stepper, plain-language topology diagrams/summaries, and contextual recommendations before each decision.
- Surface best practices when they matter. For even-sized clusters, especially two-node clusters, recommend QDevice/QNetd and explain quorum behavior and split-brain risk. Do not treat two nodes as inherently invalid: SUSE documents a two-node setup with QDevice/QNetd and fencing. Place the QNetd witness outside the cluster and preferably in a separate network or failure domain.
- Before any future mutation, show a review summary of nodes, quorum witness, Corosync links, fencing, expected changes, and blockers. Separate informational guidance from hard requirements and never present connectivity as HA readiness.

## Recommended experience

### 1. Cluster inventory

The Clusters area starts with registered hosts and their SSH reachability. Cluster plans remain separate from host records, and a SUSE HA cluster is shown as detected only after membership is reported by the HA stack. The extension currently supports read-only HA preflight and a reviewed, restricted `crm cluster init` / `crm cluster join` workflow. SUSE's interactive prompts remain visible; the extension does not silently configure Corosync, fencing, QDevice, or workloads. A saved plan remains a draft until live membership is detected.

### 2. Create-cluster wizard

1. **Select hosts:** select at least two compatible SLES hosts, display OS/release/architecture and connection freshness, and warn when hosts are already members of a cluster.
2. **HA entitlement and packages:** report SLES registration and the SLE HA extension state. Let the operator activate the SUSE extension using a one-time registration code where licensing permits. Preview package changes and repositories before applying them.
3. **Read-only preflight:** check supported release compatibility, hostname and addressing, time synchronization, active interfaces, visible watchdog devices, and TCP reachability of each peer's registered SSH port from every selected host. For QDevice plans, a failed TCP/5403 probe is informational before the first-node `crm cluster init`, because SUSE's init flow configures QDevice/QNetd and enables the service; require fresh reachability from all nodes before each `crm cluster join`. Label the TCP probe narrowly: it does not verify SSH authentication, Corosync links, QNetd identity, or cluster firewall rules. Keep Corosync interface/subnet, stable-address, and fencing checks as explicit operator confirmations until safe, SUSE-backed probes exist. Separate blockers from warnings.
4. **Topology and quorum:** select Corosync communication links, fencing method, and QDevice/QNetd placement. Explain votes and expected failure behavior in plain language. The current planner surfaces same-subnet candidates reported by every selected node, lets the operator select ring0 and optional ring1, flags subnets with dynamically assigned addresses, and requires an explicit static/reserved-address attestation. A saved draft stores only the selected subnet hints and attestation; resuming it requires a fresh review, and bootstrap rechecks that each selected subnet is still present on every node. The planner never changes host networking or answers SUSE's prompts. For a two-node cluster, visibly recommend a QNetd witness outside the cluster, ideally on a separate network or failure domain; SUSE recommends QDevice/QNetd for even-sized clusters, especially two-node clusters.
5. **Review and bootstrap:** produce a human-readable change plan. Run first-node `crm cluster init`, then `crm cluster join` on additional selected nodes as distinct operations, showing progress and per-node output. Require confirmation before every operation that changes a host.
6. **Verify and hand off:** verify node membership, Pacemaker/Corosync health, quorum, fencing, and Hawk service. Save the cluster only after the cluster reports the expected state.

### 2a. Workload templates

The extension provides read-only workload profiles for an existing service with a virtual IP, KVM virtual-machine failover, a web service, and highly available NFS. The operator selects candidate nodes and runs the same bounded SUSE preflight. A template is not marked as a candidate unless every selected node can reach every peer on its registered SSH port, in addition to matching supported SLES release/architecture, active SLE HA, `crm`/`crm_mon`, synchronized clocks, and the relevant installed SUSE OCF agents. The web and NFS profiles additionally inspect their systemd unit files; if an older API reports only service activity and cannot confirm installation, the UI marks service readiness as requiring review rather than treating the template as a candidate. The VM profile inspects libvirt storage pool definitions and reports host-local pool details.

The NFS profile makes the storage topology explicit: SUSE HA with DRBD replication or external shared block storage. The guided NFS workflow requires a quorate, fenced live cluster, a host record for each Pacemaker member, all needed agents on every member, pre-existing block devices and filesystem signatures, and existing mount-point directories. The DRBD profile is limited to two nodes and checks that the resource is UpToDate before applying. The shared profile requires stable `/dev/disk/by-id` or `/dev/mapper` paths and a user attestation that both devices refer to the same externally shared storage on every node; the extension verifies device visibility and filesystem type but cannot prove backend identity. Neither option treats a host-local libvirt pool as shared storage.

Applying the NFS profile creates the SUSE resource chain in one `crm configure load update`: separate filesystems for `/var/lib/nfs` client state and exported data, an `nfsserver` agent using `nfs_server_scope=SUSE`, an `exportfs` agent with a monitor timeout greater than the configured `stonith-timeout`, and a dedicated `IPaddr2` virtual IP. DRBD mode additionally creates the promotable DRBD clone with group colocation and promote-before-start ordering. All resources remain Stopped for operator review. The extension never partitions, formats, initializes, mounts, or starts storage. For DRBD, the operator must start the promotable clone first and verify one Promoted node with all devices UpToDate, then explicitly start the NFS group; shared-storage mode requires reviewing and then starting the NFS group. See [SUSE's HA NFS with DRBD guide](https://documentation.suse.com/sle-ha/15-SP7/single-html/SLE-HA-nfs-storage/) and [SUSE's DRBD guide](https://documentation.suse.com/en-us/sle-ha/15-SP7/html/SLE-HA-all/cha-ha-drbd.html).

The general existing-service template now has a guided service/VIP profile. It requires a service unit already installed and inactive on all registered cluster nodes, verifies Pacemaker's `service:<unit>` alias and `IPaddr2`, checks a route and confirms the VIP is not assigned on each node, and requires the operator to confirm the same client-facing network. It creates one stopped Pacemaker group with the VIP ordered before the service, then leaves activation to the operator after reviewing application bind behavior and node-local state. The profile does not install the application or alter any service/network settings. This follows SUSE's guidance that Pacemaker owns service start/stop once a service becomes a cluster resource, and that groups start members in sequence; see [SUSE's service resource classes and group behavior](https://documentation.suse.com/en-us/sle-ha/15-SP7/single-html/SLE-HA-administration/index.html#sec-ha-config-basics-resources).

The Web template now has a separate guided SUSE Apache profile based on SUSE's documented `crmsh` Apache template: it checks the installed/inactive `apache2.service`, the Apache resource agent and `ocf:heartbeat:IPaddr`, the existing Apache main configuration path and syntax, and route/VIP state on every registered member. The selected main configuration file must have the same SHA-256 digest across members. The operator must attest that Apache can start before the VIP is assigned, matching SUSE's Apache-then-VIP group ordering. It creates the `apache` primitive and `ocf:heartbeat:IPaddr` primitive in a stopped group and does not enable/disable systemd units, edit Apache configuration, install packages, or start resources. Included Apache files, certificates, modules, content, and application state are not covered by the main-file digest and must be synchronized and reviewed separately. See the [SUSE SLE HA 15 SP7 Apache `crmsh` template](https://documentation.suse.com/en-us/sle-ha/15-SP7/single-html/SLE-HA-administration/).

“Candidate” means only that these discovered prerequisites match. It does not establish production readiness or prove external shared-storage identity. A pool listed by libvirt is not treated as shared storage. The selected profile carries into the cluster planner and shows a resource/order/dependency preview in its topology and review steps. NFS configuration is a separate reviewed operation after membership, quorum, fencing and per-node storage checks pass; other templates remain previews and do not install applications or apply Pacemaker mutations.

### 3. Cluster operations

The cluster detail view should prioritize node membership, quorum, Corosync links, Pacemaker resources, fencing state, and last successful check. Offer safe operations first: refresh status, open Hawk, and maintenance-mode actions with clear confirmation and status polling. The fencing section discovers installed SUSE STONITH agents, shows the selected agent’s `crm ra info`, creates one stopped resource per selected target node, permits parameter edits only for stopped single-target top-level fencing primitives without returning stored values, and permits removal only for stopped top-level fencing primitives. Starting a fence device remains a separate, reviewed resource action.

## Safety and permission model

- Map Rancher permissions through the extension API: read-only viewers inspect status; host administrators can run host/cluster mutations. Do not infer permission from UI visibility alone; enforce it on each API route.
- Capture actor, operation, target nodes, start/end time, result, and sanitized output in the extension audit log.
- Use operation IDs and server-side state so a browser refresh does not launch a second bootstrap.
- Serialize cluster mutations per cluster and reject conflicting operations.
- Provide cancellation only before a destructive step begins; for in-progress operations report the current step and recovery guidance.
- Never claim rollback when cluster changes are not transactionally reversible. Offer phase-specific recovery steps instead.

## Practical constraints from SUSE documentation

- SUSE HA uses Corosync for membership, messaging, and quorum and Pacemaker as the cluster resource manager.
- SUSE requires at least one node fencing device for supported clusters. Fencing prevents an isolated or uncertain node from continuing to access workloads and shared data. For critical workloads, plan multiple fencing devices; diskless SBD depends on watchdog support.
- Do not infer missing fencing only from an empty Pacemaker STONITH list: SUSE diskless SBD does not create a `fence_sbd` resource. Check `crm sbd status` on every member and `sbd query-watchdog`; configuration output alone does not prove fencing succeeds.
- Quorum requires a majority of votes. Two-node partitions have no natural majority; QDevice/QNetd provides an arbitrator vote and is recommended by SUSE for two-node clusters.
- The basic two-node setup assumes static host addressing and names, time synchronization, SSH between nodes, suitable network channels, HA registered on all cluster nodes, and a QNetd server outside the cluster.
- SUSE's SLE HA 16.0 basic setup requires a separately registered SLES QNetd server with the SLE HA extension and `corosync-qnetd` installed before cluster bootstrap, and `corosync-qdevice` on every cluster node. The planner checks each package in fresh preflight. A witness can be registered as a standalone SSH-only SLES endpoint, without installing KVM or Cockpit, or can reuse an external KVM host record. Standalone registration is limited to cluster administrators, probes a supported SLES release and readiness, displays the SSH host-key fingerprint for explicit confirmation, pins that key, encrypts the password in the extension database, and exposes no credential or key material in API responses. A separate Linux username on the witness is supported. Refresh rechecks the pinned key and live prerequisites; removal deletes the encrypted registration. A reviewed package action installs only `corosync-qnetd` on the witness; another reviewed action installs only `corosync-qdevice` on selected nodes reporting it missing. Both actions require SLE HA to already be active and use existing zypper repositories. They do not activate subscriptions, start/enable services, alter firewall or network configuration, or configure quorum. SUSE's interactive bootstrap prompts for the QNetd account as needed and configures node-to-witness SSH access. The extension shows the exact `user@host` value to enter and checks only TCP/5403 reachability from the selected nodes; package preparation does not authenticate QNetd.
- Before initializing a new cluster, confirm every selected node reports the same active SLE HA product identifier through `SUSEConnect --list-extensions`. SUSE permits mixed product versions only temporarily during a rolling upgrade, not as the initial cluster state; the join path therefore remains separate so a planned rolling upgrade is not blocked.
- Interpret `SUSEConnect --list-extensions` from its product status and matching activation/deactivation command. A `Deactivate with: SUSEConnect -d ...` line is the documented command for an already activated extension; `Activate with: SUSEConnect -p ...` denotes an available extension.
- `crm cluster init` checks/configures time, SSH, firewall, Csync2, Corosync, SBD/watchdog, Hawk and optional floating IP/QDevice. `crm cluster join` adds nodes.
- Hawk requires the `hawk2` package and enabled `hawk` and `hawk-backend` services. It is available over HTTPS on port 7630 and uses the `hacluster` account by default; Hawk ACLs can refine permissions.

## Delivery phases

1. **Host inventory and design — implemented.** Existing KVM hosts are kept separate from saved cluster plans and detected SUSE HA memberships.
2. **HA discovery and read-only preflight — implemented.** Supported-release, packages, time, peer SSH reachability, candidate Corosync subnets, watchdog query, quorum, and fencing facts are surfaced without claiming unverified readiness.
3. **HA bootstrap — implemented in the extension.** Reviewed, separate `crm cluster init` and `crm cluster join` PTY workflows are available; SUSE's prompts remain interactive and host networking/QNetd/fencing are not silently configured. Automated SSH-PTY regression tests cover root and sudo execution, the sudo readiness marker before password delivery, and cleanup on early remote exit. Live validation against compatible hosts and recovery exercises remain outstanding.

The bootstrap page guides additional nodes in the saved selection order. It shows the next join target and unlocks that node only after a fresh preflight reports the planned cluster name and `crm_mon` membership for the anchor and previously joined nodes. A successful PTY exit alone does not advance the sequence. SUSE's interactive `crm cluster join` still runs as a separate, reviewed terminal session per node; the extension does not parallelize joins or treat a disconnected session as a successful membership change.
4. **Detected-cluster inventory and operations — implemented in the extension.** Status, node operations, resources, constraints, Hawk handoff, fencing/SBD facts, and audit/permission checks are available. This does not establish production readiness; cluster runtime and failure-path verification remain outstanding.
5. **SUSE resource administration — implemented with deliberately narrow safe cases.** Primitive, group, standard/promotable clone, monitor-operation, constraint, and STONITH workflows are reviewed and permission-checked. Clone deletion is limited to a stopped, top-level clone containing one non-STONITH primitive with no related constraints. A vendor-specific physical fencing connectivity test and broader recovery exercises remain future work.

## Current extension preparation

The Clusters page separates **Existing clusters**, **Plan cluster**, and **Host readiness**. The planner supports an on-demand, bounded read-only preflight for selected nodes. It reports OS/release, architecture, hostname, SLE HA activation, HA command availability, time synchronization, active interfaces, visible watchdog devices, the SUSE `sbd query-watchdog` availability result, and peer SSH-port reachability. The watchdog query is a discovery check only: it does not test fencing, and the UI does not run `sbd test-watchdog` because a successful test reboots the node. The fencing advisor marks SBD only as a candidate when every selected node's query output identifies a specific watchdog path that maps to a sysfs-reported non-softdog driver. Ambiguous output or multiple unassociated devices stays at design review; even a candidate does not prove hardware suitability, apply fencing, or validate the storage design. SUSE recommends hardware watchdogs for production and documents `softdog` for testing. For two-node clusters, the UI also calls out SUSE's limitation that diskless SBD cannot handle split brain without QDevice; disk-based SBD requires shared block storage accessible by all nodes. Its Corosync communication planner displays common subnets and per-host interfaces, warns when the detected address assignment is dynamic, and records the operator's explicit stable-address review. For QDevice plans, the wizard displays the exact SUSE prompt value (`user@host` for sudo accounts), package readiness for `corosync-qdevice` on each node, and QNetd server prerequisites. The external witness can be an imported host or a standalone SSH-only SLES registration, which does not install KVM or Cockpit. For a new standalone registration, the extension first retrieves the SSH server fingerprint without authenticating; the operator reviews and confirms it before the extension sends the SSH username or password. The extension then pins that key, checks SUSE release, active SLE HA, time synchronization, address stability and `corosync-qnetd`, and offers a reviewed package-only action. Package actions do not activate subscriptions or configure/start cluster services. Cluster plans can be saved and resumed as extension-owned drafts, with actor-scoped visibility and explicit `draft` state. They persist only selected host IDs, the chosen workload profile, current step, topology choices, selected Corosync subnet hints, and the address-review attestation; credentials and preflight output are deliberately excluded. Resume always requires a fresh operator review and reruns preflight; it never converts a draft into a cluster record. Before each `crm cluster init` or `crm cluster join`, the server reloads the saved plan, checks the operator's permission, repeats a live preflight across all selected nodes, confirms every planned Corosync subnet is still present, validates current membership, then opens a restricted PTY that runs only that fixed crmsh command. The terminal does not expose a general host shell and does not store input. SUSE's interactive prompts remain visible to the operator, with the selected ring plan shown as guidance; the extension does not configure host networking or automatically answer those prompts. Firewall policy, fencing configuration, QNetd setup, and actual cluster compatibility still require operator review and live verification. Disconnecting a running bootstrap can leave a partial setup; reconnect/replay is intentionally disabled and the plan must be rechecked before another action.

For a verified cluster, the extension exposes node standby/online/maintenance actions, primitive resource create/edit/delete and start/stop/failure cleanup, stopped resource-group creation with explicit start order, add/remove membership, reordering, standard clones for stopped standalone primitives or top-level groups, and promotable clones for stopped primitives with verified role monitors and agent actions. New primitives accept 1–16 monitor operations with interval, optional role, and timeout; standalone stopped primitives also expose a focused monitor editor that preserves parameters, meta attributes, and non-monitor operations. Promotable clones require distinct Promoted and Unpromoted role monitors and an installed agent that advertises promote/demote actions. This follows the `op monitor` and role-specific examples in the [SUSE SLE HA 15 SP7 administration guide](https://documentation.suse.com/sle-ha/15-SP7/single-html/SLE-HA-administration/book-administration.html). The editor allows the Pacemaker `interval=0` probe form and Stopped-role checks as separate operations. It does not guess resource-agent defaults: operators must validate intervals and timeouts against the selected SUSE agent's guidance. Changes require the primitive to be stopped, use an optimistic CIB operation-ID check, modify only monitor operations, and are reviewed before applying.

The cluster detail view also provides quorum and fencing status, Corosync link diagnostics, Pacemaker location/order/colocation constraints, filtered recent Pacemaker/Corosync journal output, and a direct link to Hawk. When votequorum reports QDevice, the status view also runs SUSE's read-only `crm corosync status qdevice` command and displays whether QNetd is connected, plus the endpoint and TLS state. If the command is unavailable or inconclusive, status remains unknown; the UI does not infer connection from a TCP preflight. SUSE documents this command and its `State`, `QNetd host`, and `TLS active` fields for checking QDevice/QNetd. The result is a snapshot from the queried cluster node, not proof of fencing or production readiness. Primitive resources, groups, and clones are created stopped; the user reviews each change before apply. Group members are kept together on one node, start in the displayed order, and stop in reverse order, following SUSE's documented Pacemaker group behavior. Group and clone operations are blocked when their children are active or already nested. Removing a group member leaves it configured as a standalone primitive, while deleting a group explicitly removes its member resource definitions. Resource parameters are entered as individual validated key/value fields, with the host's `crm ra info` output available as agent guidance. Constraint and resource mutations are permission-checked, reviewed in the UI, serialized against other cluster changes, and audit logged without retaining parameter values. The fencing section lists installed SUSE STONITH agents and their guidance, creates one stopped resource per current target node with an automatically assigned `pcmk_host_list`, masks credential-like inputs, allows stopped single-target devices to be edited without returning stored values, and permits deleting only stopped top-level fencing primitives. Existing fencing secrets are never returned in cluster status. Stopped top-level clone metadata editing supports clone-max, clone-node-max, globally-unique, notify, interleave, and the promoted instance limits for promotable clones. The form only edits stopped clones, preserves the child resource and unknown metadata, checks for stale configuration, and reviews changes before apply. These options follow SUSE's [SLE HA 16.1 clone configuration guidance](https://documentation.suse.com/sle-ha/16.1/html/HA-resources-configuring/) and its guidance to modify resource meta attributes through Hawk or crmsh. The UI permits deleting a stopped, top-level clone only when it contains one non-STONITH primitive and has no related constraints; the backend rechecks current state before using SUSE's documented [`crm configure delete`](https://documentation.suse.com/sle-ha/16.1/html/HA-resources-managing/index.html) operation. Clones of groups, nested clones, active/failed resources, and clone/child references from constraints stay out of scope for this one-click flow and remain manageable through Hawk/crmsh. A vendor-specific physical connectivity test remains future work; the current fencing views intentionally report configuration and reachability facts without claiming that a device successfully fences a host.

The overview metric is “Hosts reporting a cluster,” not “Detected clusters,” because readiness currently reports host-level observations and may count multiple hosts from the same cluster. Distinct cluster inventory requires verified cluster identity and membership discovery.

The fencing panel now runs the read-only Pacemaker query `stonith_admin -l <node>` for each current member and shows which registered STONITH resources map to that target. A failed query is presented as unknown; an empty result is an uncovered target. This checks Pacemaker's target mapping only: it does not contact the physical controller or issue a fence operation. SBD status remains a separate observation. SUSE documents `stonith_admin` device-list queries in its [openSUSE Pacemaker command reference](https://manpages.opensuse.org/Leap-16.0/pacemaker-cli/stonith_admin.8.en.html), and explains that checking the device connection requires the specific agent's status command in its [SLE HA fencing guide](https://documentation.suse.com/sle-ha/16.0/html/HA-fencing-configuring/index.html).
